## 实施步骤

1. 新增没有全局对象缓存的固定单字段试验函数，只支持 prepare/commit 和 2↔3 两个数量组合；没有任意字段、任意脚本或批量材料入口。prepare 只读、序列化和检查，不赋值或保存。
2. preflight 重新绑定游戏引擎和原存档，核对数量并取得身份标记。跨调用的预检只用于身份核验，不将其旧完整快照用于后续提交；不使用旧备份内容进行写入。
3. 在同一次同步 renderer 调用内取得新的 prepare 快照并立即 commit，重新检查当前值、实例契约、模式、槽位和完整快照，只赋值 protectionScrolls。完整序列化和 origin 主存档字符串只存在于调用内存中。再次序列化，将新 JSON 中该字段还原为旧值后与旧 JSON 比较；其他内容有差异就不调用保存，并在对象仍匹配时恢复这一次未保存的字段赋值。
4. 调用游戏自身 platform.save，要求同步 true，并核验实际 origin 主键和 platform.read 的完整字符串、运行时值及其他主存档。保存一旦调用后发生异常、返回不确定、存储不符或连接超时，都不自动恢复运行时、不重试写入；将结果记为不确定，先核对实际状态，避免同一次操作再次应用。
5. 主进程仅在提交核验成功后请求 flushStorageData；这是保存刷写请求，不是重启持久化证明。客户端只正常断开 WebSocket，游戏内 inspector 服务保留，由用户最终正常退出后移除临时启动参数。
6. 发送请求前在本地创建独占的阶段 dispatch 标记；相同阶段即使超时或程序退出，也不能再次发送。写入结果只记录元数据和摘要。恢复阶段要求成功的 2→3 记录，并比较当前模式/键和存档的保守身份标记；不能用旧完整 JSON 覆盖当前进度。身份标记不是游戏提供的永久唯一存档 ID，跨重启仍需用户确认同一原存档；不匹配时停止，不取消保护强行恢复。
7. 实机先写入 2→3，独立读取和观察游戏继续运行；用户确认画面、正常保存退出并重启原存档后再次核对 3。之后独立执行 3→2，用户再验证画面及重启后 2。未走完闭环，不开放全部材料或宣称稳定。

## 写代码前的三轮设计复核

1. 方向：用户要求原游戏实时材料修改，不开发独立界面、不修改游戏安装、不做堆地址猜写；本轮仅保护卷、原生序列化/保存，先证明端到端而非扩大功能。
2. 风险：旧崩溃根因未定；备份恢复和新入口只读已经验证，不因此宣称新入口写入安全。完整快照比较、可写数据属性核验、唯一主键、数量比较、构建/隔离身份和独占 dispatch 标记限制本次试验。保存开始后不自动重试或以旧备份覆盖进度。
3. 证据：自动测试需覆盖成功/还原、非法操作、数量/模式/存档变化、其他字段差异、保存失败/异步/异常、存储不符和换实例；再用精确构建的纯 Engine 在无界面隔离运行时验证序列化。实机仍须用户画面、正常退出重启及恢复确认，不能用模拟或 flush 代替。
