# 本地交付计数与不可变发布

## 设计与三遍方案复核

2026-10-12 用户授权修复后直接提交发布。主程序 0.5.3、远征 0.1.2，其它三个模块不重发。Host API 8、SDK、Schema 与远征五个页面/游戏请求不变。

1. 编号：每个项目独立，正式标签和 `delivery-versions.json` 的已交付本地编号合并后，只能取最大编号的下一位。0.0.9→0.1.0。远征已交付至 0.1.1，下一正式版必须是 0.1.2，而不是按最后正式 0.0.7 取 0.0.8。清单保留本地证据，不创建虚假标签。`build-local-package.ps1 -ModuleOnly` 成功后在独占租约下重新检查并原子登记；已交付编号不可再次交付。
2. 包：唯一构建目录，两文件候选 ZIP 逐项与源文件核对散列后原子提升。目标已存在即拒绝，不删旧包/别的游戏包。验证、压缩、移动失败只清理本次临时 ZIP；并发目标胜出者不覆盖。
3. 补传：注释标签必须在目标分支历史中；包 `ProductVersion` 等于标签提交；远端注释标签对象等于本地。目录提交推进 main 不影响重传同一资产。异源/轻标签/分支外标签拒绝；既有资产仅在散列相同后复用。
4. 顺序：源码复核→提交→干净源码构建→标签/资产→独立线上核验→目录提交→保留策略。每个游戏最多三个正式 Release；标签和本地历史包保留。完整离线包仅本地交付，不上传为宿主更新包。

方案第一遍检查计数和迁移；第二遍检查失败、同名及并发边界；第三遍检查来源、恢复和发布顺序。三遍通过后实施。主程序候选排序详见宿主 `docs/RELEASE_0_5_3_PLAN.md`：先名称，再宿主/API，再精确或动态解析候选，统一按版本排序；回退仍手动。
