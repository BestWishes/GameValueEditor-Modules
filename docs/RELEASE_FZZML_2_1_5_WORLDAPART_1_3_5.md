## 发布方案

1. 校验改动范围、独立补丁递增、清单、主题、真实页面、兼容性回归和发行工具；同步文档并提交源代码。
2. 从干净的已提交源码构建两个正式 ZIP，核对两文件结构、真实贡献者、内嵌依赖、DLL 版本和源码提交；用当前宿主实际加载全部四个模块及页面。
3. 创建带注释的两个版本标签并推送源码/标签。上传不可变模块资产，独立复验 GitHub 大小、SHA-256 与标签提交，不覆盖旧版本资产。
4. 仅在上传核验成功后由现有 CatalogOnly 脚本更新目录；提交并推送，再读取服务器目录核对版本、摘要和兼容声明。
5. 先预演、再执行每模块保留最近三个 Release 的策略；只清理这两款游戏的第四旧 Release 及资产，保留 Git 标签和本地旧 ZIP，不触碰另外两个模块。
6. 用现有完整离线构建器和正式资产生成新文件名的完整包；不覆盖用户已测试的旧包，实际验证四个 DLL、12 个页面、主程序启动和冻结收据。完整离线包仅本地提供，不上传 GitHub。

## 发布方案复核三遍

1. 范围与需求：两个游戏及稳定 ID 不混淆；模块版本独立加 0.0.1；主程序保持 0.5.2；小更新不因历史哈希被整包拒绝；没有未经授权的游戏数值写入。
2. 资产与目录：源码提交先于构建；注释标签绑定构建提交；线上资产先于目录；正式包不混入本地测试构建，不伪造贡献者，不覆盖已发布资产。
3. 回退与交付：最多三个版本按模块分别计数；删旧 Release 不删 Git 标签；新完整包新文件名，保留旧包及收据；未实测修改/持久化不声称已实测。
