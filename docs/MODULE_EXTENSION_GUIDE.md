# 游戏专属模块与游戏内编辑模块扩展规范

## 术语和身份

游戏专属模块代表一个游戏，稳定 ID 形如 `game.example`。游戏内编辑模块代表游戏中的一项功能，稳定 ID 形如 `game.example.inventory`。中文名称只是显示文本，发布后改名不能改变稳定 ID。

同一游戏包可以注册多个编辑模块，但同一包内 ID 不得重复。编辑模块按 `order`、再按稳定 ID 排序，并在主程序“本游专属”页的竖向导航中展示。

## Host API v4

公共契约位于 `sdk/GameValueEditor.ModuleSdk`。Host API 4 新增模块页面注册和字段生命周期策略；API 4 模块必须明确注册每个编辑器对应的标准页面角色，旧的 API 2/3 模块继续通过固定的 CLR 程序集绑定版本与通用兼容层加载。任何新增公开契约都必须提升 Host API 并同时重建宿主与对应模块，不能让新模块伪装成旧协议兼容。模块单独构建通过不能证明运行期 ABI 兼容：完整离线包还必须实际加载模块并调用至少一个新增契约入口。

- `IGameAdapter`：游戏包身份、构建匹配、编辑器描述与快捷入口读写。
- `IInventoryGameAdapter`：标准 `collection` 背包/集合界面。
- `ICharacterAttributesGameAdapter`：标准 `master-detail` 人物属性界面。
- `IEntityEditorsGameAdapter`：通用实体/数字字段界面，适合装备、材料、进度等不应被硬塞进背包或人物属性的数据。实体 ID、字段 ID 必须是稳定语义身份；模块提供范围和可写状态，宿主统一提供查找、双击修改与快捷入口。
- `IGameVersionMetadataProvider`：可选的游戏自报版本、产品名和构建 GUID；只用于帮助用户识别版本，不能代替安全构建验证。
- `IGameEditorPageProvider`：模块拥有的页面清单，把稳定编辑器 ID 显式绑定到 `Inventory`、`CharacterAttributes` 或 `Entity` 标准页面角色；主程序不得再按 ID 后缀、游戏 ID 或声明顺序猜测页面。
- `IGameEditorFieldPolicyProvider`：可选的字段级生命周期和锁定策略，适合一个页面同时包含持久化字段与仅本次运行字段的情况。
- `GameEditorDescriptor`：编辑器 ID、显示名、类型、顺序、描述和 `SessionOnly`。
- `ModuleFieldKey`：由编辑器 ID、实体 ID 和字段 ID 组成快捷入口语义键。

模块项目引用 SDK，但 ZIP 只包含模块 DLL 与 `module.json`。宿主提供 SDK 程序集，避免加载两份契约类型。

## 标准界面类型

- `collection`：平面集合表格，例如背包物品。
- `master-detail`：左侧实体、右侧字段，例如人物属性。
- `property-grid`：单对象键值属性；契约已保留，新增宿主模板时应保持相同数据模型原则。

游戏模块决定有哪些页面、页面顺序、显示名称、说明、空状态和对应操作能力；宿主只渲染固定的标准模板，并统一管理主题、布局、忙碌状态、弹框、批量选择和错误显示。普通新增游戏只新增模块代码，不得要求主程序增加游戏 ID、页面名称或固定 Tab。

## 目录与清单

每个游戏放在 `games/{短名}`。`module.json` 是人工维护的唯一事实来源，必须声明：稳定游戏 ID、模块版本、模块显示名、游戏显示名、说明、程序集、Host API 版本、进程名、精确兼容构建和编辑器列表。不要在 `catalog.json` 重新手工维护这些重复信息；发布脚本会从源清单生成目录条目。

同目录的 `contributors.generated.json` 由维护者通过 `scripts/update-contributors.ps1` 生成，不接受贡献者自行修改。它记录整个游戏专属模块的 GitHub 显示名称、主页、首次贡献日期和最新贡献日期，不细分到具体编辑模块，不记录贡献次数、排名或内容。GitHub 登录名作为稳定身份。

一个游戏包版本发布后不可替换其 ZIP。任何二进制变化都必须提升版本。先创建并验证 Release 资产，再提交指向该资产的清单。

标准发布顺序是：提升 `module.json` 与项目版本；运行 `validate-modules.ps1 -SkipCatalog`；运行对应 `publish-*.ps1 -SkipCatalog` 构建 ZIP；创建不可变 Release 并上传 ZIP；下载或查询线上资产校验 SHA-256；最后把已验证的版本、URL 和哈希写入 `catalog.json`，执行完整验证后提交推送。这样客户端永远不会先看到一个尚不存在的下载地址。

## 本地验证与人工边界

仓库不依赖 GitHub Actions。维护者在可信本地环境运行 `scripts/verify-release.ps1`，检查稳定 ID、编辑器 ID、正式语义版本、三重哈希、贡献者数据结构、目录一致性并构建全部模块；PR 源码不能在包含游戏进程或用户凭据的环境中未经复核直接执行。

本地脚本通过不能证明内存写入安全。维护者仍需核对：只面向离线单机游戏；未知构建安全失败；没有宽泛偏移或绕过逻辑；写入对象、线程、缓存/事件、保存和回读链路有证据；最小值实机验证不会破坏存档。审核目标是检查规则和证据，不是让贡献者之间形成名次或“明星作者”归属。

## 构建兼容

首选核对 EXE SHA-256；Unity IL2CPP 游戏应同时核对 `GameAssembly.dll` 与 `global-metadata.dat`。不得使用窗口标题、显示版本或文件时间代替构建身份。

只有在已经证明小版本的对象布局与关键机器码全部不变时，才可提供结构签名回退。若游戏保留 IL2CPP 导出元数据，也可优先按程序集、命名空间、类型、字段、方法名和参数数量解析当前构建的实际地址；解析结果必须验证属于目标 GameAssembly，并覆盖模块真正使用的根对象、业务写入、刷新/保存与版本入口。任一语义成员缺失、类型结构异常或函数地址越界都必须拒绝适配。不能只核对一两个“看起来稳定”的序言，更不能使用通配偏移。

模块中心目录先按 `processNames` 让客户端发现当前游戏的最新包，再把精确 `compatibleBuilds` 作为“服务器已明确收录”的提示。目录未登记当前哈希时仍可下载安装，真正启用前必须由模块 `Supports` 对精确哈希或完整结构签名作最终判断。

游戏包可以支持多个精确构建。某个编辑模块若只支持其中一部分构建，必须在自己的能力判断中安全失败，让宿主显示“当前构建暂不支持”，不能影响同包其他编辑器。

## 字段与生命周期

实体、字段和快捷入口都使用稳定语义键。每次操作重新定位对象，不保存堆指针。写入流程必须：验证进程和构建、定位并核对对象、校验旧值和范围、在正确线程执行、调用所需缓存/事件/保存流程、回读真实值。

持久化编辑器应验证重启后仍正确。`SessionOnly` 编辑器或字段必须在描述和 UI 中明确“关闭游戏后失效”，不得锁定或在连接/重启时自动重应用；混合生命周期页面使用字段策略声明，主程序不得按具体游戏 ID 特判。

## 主线程挂接

Unity/IL2CPP 操作通常需要主线程。一次性挂接应校验函数序言，保存并恢复原始字节和页面保护，使用状态字与硬超时。若目标线程可能仍在执行，宁可保留少量远程内存，也不能提前释放造成崩溃。

不得默认所有 IL2CPP 泛型方法都能把 `MethodInfo*` 置空调用。若目标方法属于构造泛型实例，应从当前真实对象的 `Il2CppClass*` 调用 `il2cpp_class_get_method_from_name` 获取该实例对应的方法元数据，并在业务调用时按该构建的实际调用约定传入。这样既能让字典自行扩容，也不会手工破坏托管集合的桶、版本号或写屏障。

## WorldApart 参考实现

`game.worldapart` 用一个游戏包注册两个游戏内编辑模块：

- `game.worldapart.inventory`：以物品配置 ID 为实体语义身份，重新定位当前玩家背包中的堆叠，修改后刷新背包并调用游戏自动存档。
- `game.worldapart.character-attributes`：以当前玩家和属性类别/配置 ID 为语义身份，覆盖资源、基础属性、探索属性、五行灵根与战斗属性。`CombatModel.CultivateExp` 映射为“基础属性 · 修为”，`CombatModel.CultivateReserveExp` 映射为修炼/突破界面的“资源 · 灵气”，不能与人物面板的“基础属性 · 灵力”混用。

该游戏的经验可复用于其他 Unity IL2CPP 适配器：只读查询线程不能调用隐含主线程依赖的聚合 getter；能直接表示目标含义的持久化字典应优先于临时界面缓存；缺失的五行灵根键必须通过字典自己的 `set_Item` 写入，不能假设固定容量后手工填槽；每次写入都要在游戏主线程执行保存并回读。模块只提供数据与语义名称，人物属性名称筛选由宿主统一实现。v1.2.0 优先核对三个构建文件；若第三方发行版只替换启动 EXE，而 `GameAssembly.dll` 与 `global-metadata.dat` 同时命中同一已验证布局，则允许忽略启动器哈希和安装路径差异。元数据目录只能从同名 `_Data`、`WorldApart_Data` 或安装根目录唯一的可验证 `_Data` 中选择。其余未知构建必须通过全部关键读取、写入、保存、主线程钩子和版本入口的结构签名验证；任一项变化都拒绝套用。模块还通过 Unity `Application` API 提供游戏自报版本、产品名和构建 GUID，宿主与 Steam Build ID、引擎文件版本分开显示。

## Last Epoch 参考实现

`game.last-epoch` 展示了 Unity IL2CPP v39 游戏中“按玩家真实需求缩小编辑面”的做法：点数写入必须遵守 XP/等级权威链；五维与倍率从 `PlayerFinder.playerActorComponent -> Actor.stats` 的实时权威对象读取；装备只定位熔炉主槽当前物品，以 `ItemData.individualID` 作为本次操作语义身份；资源必须包含尚未持有、数量为 0 的定义，并从 `Localization._tableCache` 读取当前语言名称；异界只编辑已有记录，绝不创建时间线或解锁剧情。地图迷雾已经永久移出交付范围；仅存在场景生成临时字段时，也不应把怪物数量倍率包装成可复用功能。

从 v0.2.0 起，该模块不再把小版本兼容等同于“哈希必须完全相同”。清单仍登记实机验证过的三重哈希用于审计和服务器提示；运行时则通过 IL2CPP 导出接口按稳定语义重新解析 `PlayerFinder` 根字段、人物/物品字段、`ItemData` 与 `ItemContainerEntry` 方法以及 Unity `Application` 版本入口，并校验函数指针位于当前 `GameAssembly.dll` 内。这样函数 RVA 因小更新整体平移时无需重新人工找地址，同时字段或方法被删除、改名或结构异常时仍会安全失败。

该模块还记录了三条必须遵守的失败边界：角色保存入口必须在 Unity 主线程调用；装备写入前必须重新读取熔炉主槽并核对 `individualID`；不得从注入工作线程调用 `Object.FindObjectsOfTypeAll` 等 Unity 对象枚举。运行期人物统计通过一次性虚表挂接在游戏自己的 `CharacterStats.OnUpdateTick` 主线程上下文调用 `AddStatModifier` 与 `UpdateStats`，随后从最终属性字典、冷却缓存、技能创建逻辑或实际结算入口验证。禁止把模块自己写入的临时记录再读一遍当成成功；没有进入游戏最终计算结果就必须报错。任何会导致进程退出的游戏业务函数，即使方法签名看似正确，也不能交付。

Last Epoch 的实测进一步形成以下通用规则：通用冷却必须写游戏真正读取的 `addedValue` 并刷新充能缓存；移动技能冷却必须修改会重建派生值的上游能力记录，不能直接写一次施放后就被覆盖的缓存；经验、总物品掉落率和金币倍率必须挂到最终结算或落地入口，并用真实结算计数验证；效果范围可同时影响碰撞范围和技能视觉，不应为了单个技能另加破坏统一语义的补丁。只有 getter、派生缓存或静态字段读写证据的近战范围、金币堆频率，以及会干扰正常品质生成的暗金/套装分类掉率均不交付。发现某项功能只能靠危险钩子或会吞掉其他掉落时，应删除字段、兼容校验、写入路径和诊断入口，而不是只隐藏界面。

若某项游戏函数只能在 Unity 主线程安全运行，模块必须通过游戏现有 PlayerLoop/同步上下文排队执行，并等待完成标记后复读；禁止把会崩溃的附加线程直接调用交付给用户。字段状态必须区分写入存档与仅本次运行有效。

分析时先用当前三重构建指纹生成结构映射，再从 `PlayerFinder` 的运行期 getter 重取人物、技能树、物品容器和全局材料根对象。读取旧的同构建本地存档只能用于理解尚未进入内容的数据形状，不能把旧存档的记录、地址或进度注入当前角色。对尚未持有的集合成员，要调用游戏自己的对象工厂和容器添加方法，而不是直接伪造托管列表节点。每次写入均执行游戏对应的脏标记/保存路径并回读权威对象；未知构建、非离线启动和未加载对象都安全失败。

## 验收清单

- 构建、清单、模块包和 SHA-256 一致。
- 正确游戏/构建加载，错误游戏或未知构建拒绝。
- 所有实体稳定枚举，切换后不复用旧地址。
- 最小写入立即生效并回读一致。
- 持久化/仅会话行为与声明一致。
- 人物面板、实际技能、经验结算、掉落实物或最终消费点至少有一项与功能语义直接对应的验收证据；内部字段写回不算完成。
- 异常输入、对象未加载、结构变化和超时安全失败。
- 一个游戏包能同时装配至少两个编辑模块且数据不串页。
- `module.json`、包内清单、贡献者生成文件、`catalog.json` 和 Release ZIP 版本/哈希一致。
