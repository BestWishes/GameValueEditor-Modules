# 宝石基础属性满值补修（本地 0.1.1）

## 问题与详细方案

用户反馈新生成宝石仍有一项基础属性没有取满。当前游戏 0.116.92 的宝石同时保存独立 `bonus` 与 `affixes`。上一版只发现 rollAffix/roll 的数值位置，且校验要求整个根对象不变，因此把 bonus 当作不允许变化的字段，漏掉了它。发现样本 .5 又总产生固定 bonus=0 的泥土石，未覆盖有范围的宝石。

当前包 `mining-data.GEM_TYPES` 有十类：泥土石、蛋白石、牛角石、海螺石、翡翠石、流体石、血晶石、元素石、天空之泪、非洲之心。原生 makeGem 的类型选择与 bonus 数值使用不同随机调用；七类有随机范围，另三类为固定值。纯工厂逐项端点对照确认保持类型/词条不变时可由原生公式取合法上限。范围来自当前定义，不把这些数值写死在宿主或模块。

1. 读取当前 GEM_TYPES 的语义键、min/max；由纯 makeGem 生成采样种子映射到各类型，不携带主进程调用坐标。
2. 在当前 renderer Engine 的隔离打磨副本中覆盖这些样本。允许比较时仅移除宝石 bonus 和词条数值，类型、品质、UID、tier、词条选型与其它字段仍严格一致。只接受 bonus 增大到对应当前定义上限的数值调用点；不得把类型选择随机数映射成最大。
3. 将发现的 bonus 调用点加入现有同 Engine 的生成随机映射，仍要求 makeGem 原生栈；原随机函数只消费一次。没有旧宝石回写、原型修改、工厂替换、游戏文件或保存改写。固定基础属性不额外修改。
4. 装备会话实现版本 3→5（4 为本轮隔离检查中的中间实现），模块 0.1.0→0.1.1；旧版已应用开关保留可恢复，不自动覆盖。页面补充“宝石基础属性与附加词条”，保持现有页面和稳定 ID；主程序不改。
5. 既有商城/转盘检查增加 bonus 上限断言；另分组验证十种宝石×四品质×单次/批量打磨，以及转盘单抽/十连×三种额外奖励。维持原请求超时，用固定 gem-base/gem-wheel 只读枚举扩展验证，不能运行用户脚本。所有消费者、结算、保存重载仅作用于副本。
6. 通过回归、当前原生消费者、真实宿主加载与完整包验证后输出新短名 202610115，保留旧包，不提交、不推送、不发布。

## 编码前复核（三遍）

1. **根因与语义**：通过拥有的无窗口 native 进程逐类确认 bonus 单独变化；当前定义与工厂范围相符。固定属性与随机范围分开，旧宝石仍不在范围。未把“取最大类型”误当“原类型数值取满”。
2. **边界与组合**：复用模块内生成 RNG，不加宿主分支；同 Engine/当前工厂动态发现，保留类型选择、RNG 次数、概率编辑器组合及恢复归属。测试比较必须保留非数值字段并检查旧库存，不能只放宽 shape 而不验证 bonus。
3. **回归与交付**：新增会失败的 bonus 测试和十类消费者覆盖，旧版活跃规则明确可恢复；分组避免单次大矩阵超时。版本/说明一起更新，打包沿用主程序既有完整离线入口，新文件不覆盖旧文件。

## 编码后复核

### 第一遍：根因、调用路径与修改边界

- 两个新增用例均先复现失败，再修到通过：基础 bonus 未取满；经模块导出对象调用 makeGem 时的栈显示别名不同。
- 原生打磨使用 `makeGem`，转盘使用 `Object.makeGem`。只规范化这一个函数显示别名，仍保留当前包路径、行列坐标并在当前 Engine 上动态发现，不写固定地址或历史坐标。中间版本打磨通过而转盘海螺石仍为 4（原生上限 5），已由转盘测试暴露并补修，不能用打磨结果替代转盘验证。
- 基础属性上限读取当前 GEM_TYPES。比较只放开 bonus / affix 数值，原类型、品质、UID、词条选型、消耗与随机调用次数保持一致。没有旧宝石回写，也没有宿主专用分支；已应用的旧实现 3 可先恢复，再加载实现 5。
