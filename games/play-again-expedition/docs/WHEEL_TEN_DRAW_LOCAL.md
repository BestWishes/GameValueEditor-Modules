# 大转盘十连抽：本地修复

## 范围与原因

本轮仅修改远征模块和它实际嵌入的概率脚本，不修改主程序、游戏安装文件或玩家存档，不提交、不发布。完成后提供完整离线测试包。

当前正常启动的游戏为 0.116.92。用相同 Electron 运行时加载当前 `app.asar` 的原生 Engine，在历史存档的隔离内存副本中复现：配置 100% 装备保护卷，单抽命中；原生 `spinLuckyWheel(10)` 只有第一抽命中。十次奖格和额外奖励拦截均被调用，但后九抽仍使用旧奖盘的索引计算，因此调用次数不代表实际效果。

原生单抽和十连抽共用 `spinLuckyWheel(count)`。十连抽在函数内部逐次产生新奖盘，直到批次结束才回写外部 `state.luckyWheel.board`；不能一直读取这个外部字段，也不能固定保护卷所在格子。

## 详细设计

1. 保留原生抽奖函数完整执行，不拆成十个模拟单抽、不事后替换奖励、不重算扣券、进度、动画或保存。
2. 当前原生 `chooseWheelIndex(board, rng)` 在选择奖格时提供真实奖盘。仅在模块已有的 Engine RNG 临时包装中，使用固定的非严格模式桥接函数读取这个原生调用的实参。桥接由固定函数字面量编译，不能使用 `eval`/`Function` 或放宽游戏 CSP；其它验证/控制工厂仍各自运行于严格模式。要求调用者语义名和传入的 RNG 身份一致，再由已有当前包调用位置检查限定最终消费者。读取的奖盘只用于权重映射，不修改奖盘。
3. 同一套五类概率、类内权重、双倍/跑马灯规则逐抽适用。保留原生 RNG 次数和其它随机结果；不改 `Math.random`、全局原型或其它 Engine 实例。临时 RNG 仍在 `finally` 中恢复。
4. 调用者实参是当前原生代码已确认的能力，不是通用 JavaScript 保证。如果后续消费者不再提供这个能力，不拿旧奖盘伪装成功；记录明确的规则未生效状态。单抽和十连抽都必须使用实际消费者奖盘。
5. 更新模块会话实现编号。旧规则安装时仍允许读取和恢复，避免旧包装与新包装叠加；恢复旧规则后再应用新版。恢复任一规则不会撤销真实奖励或清除另一内容编辑器的规则。
6. 自动测试使用会改变奖盘布局的十连抽模型，以及当前游戏真实原生 Engine。正式 renderer 路径只读取原状态，抽奖和结算测试在独立内存副本中执行，不消耗玩家转盘币。

## 编码前三遍检查

- 第一遍（方向与边界）：问题在实际每抽奖盘，而不是缺少十连抽按钮或新的主程序接口。修复留在游戏模块。
- 第二遍（随机与结算）：保留原生批次，仅映射目标消费者的一次随机值；不额外抽取随机数、不干预奖励对象和原生结算。
- 第三遍（生命周期与交付）：只读获取消费者实参、临时 RNG 清理、旧规则可恢复、掉落规则隔离；完整离线包使用已有组包入口，不能覆盖正式包或修改 catalog。

## 编码后三遍检查

### 第一遍：差异、方向和生命周期

逐项复核模块差异：真实奖盘来自奖格选择消费者的只读实参，不固定任何奖品索引，也不把批次改为十次人工单抽。原生函数只执行一次，RNG 原接收者、参数和非目标随机返回值保留；异常路径恢复临时 RNG。未改全局随机、数组原型、主程序、SDK/API、游戏安装文件或存档。

旧会话仍可读、可恢复，恢复大转盘不会删除掉落规则。待两边旧规则都恢复后，新实现重新建立身份回执；没有叠加包装或自动撤销真实奖励。模块本地版本独立递增为 0.0.7，服务器目录与官方 0.0.6 资产不改。
